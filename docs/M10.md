# M10 — Offline strategy validation and walk-forward testing

M10 evaluates the **existing legacy** `Strategy` and `backtest.run` path. It introduces no trading rule, fill generator, broker connection or parameter recommendation. M7–M9.3 remains a separate, committed signal/risk/simulation pipeline: it requires caller-supplied historical context, risk inputs and explicit simulated fills. No complete entry/exit strategy or verified historical fill archive exists for that pipeline, so M10 does **not** report M7–M9.3 returns or profitability.

No historical BTC/ETH market CSV or parquet file is tracked in this repository. The normal tests use deterministic synthetic fixtures. Empirical performance validation therefore remains unavailable until a provenance-checked dataset is supplied.

## Components and inputs

`trading/validation.py` accepts one completed `(summary, equity, trades)` result from `backtest.run` via `evaluate_completed_run(...)`. The caller must supply a source ID, BTC/USDT or ETH/USDT symbol, `5m` timeframe and explicit account unit. It checks chronological UTC equity, complete trade identities and timestamps, explicit fee/slippage assumptions and their agreement with the parameter record, trade gross minus fees plus funding, fill and settlement audit totals, net P&L against final equity, and event drawdown against the original summary. The report carries the fee/slippage bps and a canonical SHA-256 of the parameter record. Missing or inconsistent inputs raise instead of becoming zero.

The report reuses the legacy simulator's total return, realized trade accounting and event drawdown. It adds trade-level rows, attribution by asset, timeframe, regime and side, expectancy, win/loss/flat counts, profit factor availability, and drawdown duration from the last event-equity peak through recovery or a censored end. Legacy trades do not identify a unique signal category, so that dimension is explicitly unavailable. Cash slippage cannot be separately recovered from fills already priced with adverse slippage; the configured bps remain in the original summary.

Sharpe and Sortino use **regular 5m equity returns**, not irregular risk-event samples. The default minimum is 30 days of contiguous 5m returns (8,640 returns), with a zero risk-free baseline and 365-day annualization. Insufficient samples, irregular cadence, zero variance or no downside produce an unavailable reason rather than a numeric zero. This guard is not evidence of statistical significance; dependence, nonstationarity and multiple testing remain limitations. A smaller minimum can be passed explicitly for synthetic unit tests.

`compare_benchmark(...)` requires an independently supplied, already-costed benchmark equity curve with the same start/end timestamps and account unit, explicit availability timestamps, source ID and cost provenance. It reports the difference in percentage points. It does not create buy-and-hold fills or assume zero costs, FX, or a benchmark dataset. The caller is responsible for benchmark accounting and price provenance.

`trading/walk_forward.py` supplies `WalkForwardConfig`, `plan_windows`, `walk_forward`, and `sensitivity_in_sample`. A config fixes train/test/step lengths, optional purge bars, embargo bars, and rolling versus expanding training. Test windows do not overlap. Purge removes the final specified bars from the training evaluation; embargo excludes bars between the training boundary and the next test window. Those bars can still be used as historical indicator warmup at a later test decision, because they were available then. The module requires an explicit data cutoff and the existing `trading.data.validate` rejects unfinished, missing or causally late candles/observations.

For each fold, the runner supplies only the data prefix ending at that fold's train or test end to the existing simulator. The parameter set is fixed across folds; no out-of-sample result is used to choose it. Each train and test run starts with fresh legacy capital and force-closes an open position at its own boundary. Returns from separate windows must not be compounded as if one continuous portfolio. `WalkForwardReport` records the source ID, normalized input SHA-256, config, parameter hash, folds and limitations. `sensitivity_in_sample` evaluates explicit parameter/cost scenarios **only within one training window** and does not select a winner. Scenario parameters are copied into immutable report tuples.

## Existing execution and risk policy

All fills, stops, target logic, fees, slippage and optional funding settlement remain in `backtest.run` and `trading.ledger`. M10 does not reprice or fabricate them. The legacy strategy default risk fraction is 0.25% of its own numeric capital, as documented in M0–M2. This legacy policy is distinct from M8's user-selected experimental **10% of current portfolio equity** planned-loss cap. M8 and its 10% policy are untouched and are not claimed to be active in legacy walk-forward runs.

The legacy strategy substitutes neutral values for some missing optional inputs. M10 carries the simulator's observation-availability report forward and flags absent or assumed-at-close observations, funding settlement not tested or unverified, unspecified signal category and unseparated cash slippage. These conditions limit interpretation of any later historical result. An explicit historical funding-event column is required to test funding debits/credits; even then, schedule coverage is not independently verified.

## Acceptance and current limits

Focused tests cover trade/accounting reconciliation, drawdown duration, no-trade and inadequate-return cases, malformed artifacts, cost sensitivity, aligned benchmark eligibility, exact walk-forward boundaries, purge/embargo, expanding windows, fixed parameters, train-only sensitivity, future mutation and unfinished-data rejection. `docs/coordination/M10-TESTS.txt` records fresh execution commands and results after the complete suite runs.

M10 is an offline evaluation framework, not a historical profitability result. A real evaluation still needs authenticated BTC/ETH OHLCV, explicit account/quote FX if the account is INR, exchange fee/slippage assumptions, settlement events and timestamps, and a full M7–M9.3 strategy/fill specification before that stack can be evaluated. There is no M4 news dependency, network access, live/paper execution, Telegram delivery or new dependency.
