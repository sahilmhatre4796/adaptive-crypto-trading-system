## Architecture and boundaries

`trading/notifications.py` contains immutable notification/failure/template models, pure `notification_events(source, *, as_of, order=None)` mapping, and `render_notification(event, config)` HTML previews. `trading/notification_outbox.py` contains an isolated in-memory queue and append-only simulated delivery history. Corresponding focused tests are `tests/test_notifications.py` and `tests/test_notification_outbox.py`.

The mapper accepts immutable producer **records**, not SignalTracker/RiskEngine/Portfolio/bridge actors, transports, hooks or callbacks. It reads source values and returns copied scalar/Decimal/timestamp/tuple metadata. The outbox stores only those normalized values and rendered strings. Neither module calls risk evaluation, reservation management, order processing, accounting or execution methods. Notifications are reporting artifacts, never approval inputs. The experimental 10% current-equity M8 risk policy remains untouched.

There is no Telegram SDK, API client, HTTP request, bot token, recipient ID, secret field, exchange connection, installation, network operation or external service. `TELEGRAM_OFFLINE_PREVIEW` and HTML parse mode describe local delivery-ready **content**, not real Telegram delivery. DELIVERED_SIMULATED is a local state with no external acknowledgement. No runtime/platform-format compatibility, paper-trading readiness or profitability is claimed.

## Event mapping

| Source | Notifications |
| --- | --- |
| Qualified M7-v1 SignalRecord | SIGNAL_QUALIFIED, with actual pattern/confirmation timeframes and original qualification availability. It explicitly asserts analytical qualification only, not M8 approval. |
| M8-v1 RiskDecision | RISK_APPROVED, RISK_REDUCED, RISK_REJECTED or RISK_BLOCKED, exactly matching its status. Quantity, planned-loss budget, planned loss, currencies, configuration/input IDs and exact reason-code tuple are retained. |
| M9.1 OrderIntent | ORDER_INTENT_CREATED, clearly SIMULATED. Full source quantity, identity and original expiry are retained. |
| Accepted M9.1 AdmissionReceipt | Canonical risk and intent notifications; these deduplicate against direct risk/intent inputs. |
| Denied M9.1 AdmissionReceipt | INTEGRATION_DENIED. It cannot become an approved notification even when a prior M8 grant was positive but ingress later became stale/ineligible. Original M8 status remains separately labeled. |
| ENTRY_FILLED LifecycleEvent + matching OrderIntent | SIMULATED_ENTRY_FILL then SIMULATED_POSITION_OPENED, two distinct views of one immutable booked source event. |
| EXIT_FILLED LifecycleEvent + matching OrderIntent | SIMULATED_EXIT_FILL then SIMULATED_POSITION_CLOSED. |
| ORDER_CANCELLED / ORDER_EXPIRED LifecycleEvent + intent | SIMULATED_ORDER_CANCELLED / SIMULATED_ORDER_EXPIRED. |
| SIGNAL_INVALIDATED / SIGNAL_EXPIRED from pending order | Simulated cancellation/expiry according to the producer's actual state transition. |
| Terminal notice on an already-open/closed/canceled/expired order | SIMULATED_SIGNAL_TERMINAL_NOTICE retaining its state. An OPEN notice does not imply a close or execution. |
| Structured ProcessingFailure | PROCESSING_FAILURE or INVALID_LIFECYCLE, ERROR status, explicit public reason codes, stage and supplied observation/availability. No raw exception or traceback input is accepted. |

M9.1's ORDER_PROPOSED lifecycle view normalizes to its matching canonical OrderIntent rather than emitting a second intent alert. Its identity/linkage/timestamps are checked; the business-source reference is the original order ID. Raw SimulationFill/SimulationCancellation requests do not prove booking and are not notification sources: use the resulting M9.1 LifecycleEvent. Missing order joins, contradictory status/quantity/allocation, unknown kinds/schemas, unmatched IDs and invalid transitions raise rather than create an invented notification.

M8/M9.1 records do not contain a timeframe. That field stays None and the preview says “not supplied by source”; the mapper never assumes 15m. Source prices use explicit quote currency (USDT), while budgets/planned loss use the source account currency (for example INR). Missing data remains None or rejects a required source field; it is never silently replaced with zero. A genuine zero quantity on a rejected decision is retained.

## Typed contracts and provenance

`NotificationEvent` fields: kind, source_kind, source_id, source_fingerprint, source_available_at, status, reason_codes; optional symbol, side, timeframe, confirmation_timeframe, observed_at, upstream_available_at, signal_available_at, expires_at, signal_id, risk_decision_id, order_id, allocation_id, source_configuration_id, source_input_id, risk_status, quantity, price, price_kind, price_currency, risk_budget, planned_loss, currency, failure_stage, related_event_id; schema_version=M9.2-v1, computed event_id and dedupe_key. All fields are immutable and IDs are computed from canonical values.

`ProcessingFailure` requires failure_id, kind, stage, exact public reason-code tuple, observed_at and available_at. Related event ID, symbol, side and known timeframe are optional. The caller supplies a stable identity for one failure occurrence; distinct later occurrences need distinct source IDs. It must select safe public codes, never credentials, raw exception text or tracebacks. No automatic secret scanner or arbitrary payload redactor is claimed.

Producer schemas/types and relevant state/identity relationships are validated. This is not cryptographic authentication or a replacement for the source actors' authority checks. Typed immutable records and honest point-in-time provenance remain a trusted in-process boundary; untrusted wire imports and producer-history authentication are not implemented. Notification facts cannot authorize a risk/order operation, including manually constructed reporting objects.

Timestamp meanings remain independent:

| Field | Meaning |
| --- | --- |
| source_available_at | Original availability of the mapped producer fact: M7 decision, M8 decision, M9 intent creation or M9 lifecycle processing. |
| signal_available_at | Original M7 signal availability, copied through M8's proposal; never replaced with notification/enqueue time. |
| upstream_available_at | M3 pattern availability for qualified signals; M8 decision availability for intents; original fill/cancellation/upstream notice availability for lifecycle facts. |
| observed_at | Actual supplied confirmation close, fill/cancellation observation or failure observation, when the source exposes it. |
| expires_at | Original signal expiry, retained as historical context. A close notification after that expiry remains a valid recorded fact. |
| Outbox enqueued_at / updated_at | Actual explicit local enqueue and simulated delivery cutoffs, separately recorded. |

There are no implicit wall-clock reads or generated source timestamps. Future producer facts are rejected before enqueue. Delayed historical notifications preserve their original source times; they are not current trade recommendations. Existing UTC normalization is reused. The mapper does not reevaluate signals or reset freshness/expiry.

## Templates and escaping

Every preview has a fixed OFFLINE header; all order, fill, position, cancellation and integration-denial headers explicitly say SIMULATED. Status labels come from validated enums, not free text. Relevant symbol, side, timeframe, quantity/price units, budget, exact codes, timestamps and source/correlation IDs are shown. Qualification explicitly says that M8 approval is not asserted. Reduced decisions retain their reduced size; rejected/blocked headers cannot be relabeled APPROVED.

Only template-owned `<b>`/`<code>` tags are emitted. All source values are HTML-escaped, including quotes. Control/newline, bidi-control and unpaired-surrogate characters are rendered as visible escapes to prevent label/markup spoofing and invalid UTF-8 output. Original reason-code strings remain exact in structured events; escaping is display-only. No external links, traceback rendering or raw HTML input is supported.

`TemplateConfig(max_message_characters=...)` requires an explicit positive local preview bound. It counts encoded HTML string characters, not a verified Telegram API limit. Oversized messages raise without silently truncating reason codes or IDs. No automatic splitting, Markdown mode, locale translation or platform-limit assumption is implemented.

Example visible excerpts from synthetic fixtures (full records also retain source IDs/timestamps):

```text
OFFLINE | RISK REJECTED
Symbol: BTC/USDT
Side: LONG
Status: REJECTED
Source quantity: 0 contracts
Planned-loss budget: 200 INR
Reasons: EXCHANGE_MINIMUM_NOT_AFFORDABLE, PER_TRADE_RISK_LIMIT
```

```text
OFFLINE | SIMULATED POSITION OPENED
Symbol: BTC/USDT
Status: OPEN
Source quantity: 20 contracts
Simulated fill price: 100 USDT
```

## Offline outbox and delivery simulation

`OfflineNotificationOutbox(config)` accepts no engine or transport. `enqueue(event, *, as_of)` returns a frozen `OutboxEntry`: notification, rendered message, monotonically increasing sequence, enqueued_at, state, attempts and updated_at. The rendered record contains message_id, notification_id, template_configuration_id, body_html, parse_mode=HTML and channel=TELEGRAM_OFFLINE_PREVIEW. There is no destination or credential.

`entries`, `pending()`, `get(notification_id)` and immutable `history` support inspection. FIFO sequence is **arrival order**. A delayed older producer fact appends later; no existing entry is reordered or backdated. Multiple mapped views preserve deterministic tuple order (entry-fill before position-open, exit-fill before position-close). Callers enqueue each event separately; no atomic multi-event batch is claimed.

Event IDs hash normalized source facts; dedupe keys identify source kind/source ID/notification kind. A separate source-facts signature spans all views of a source ID, preventing revised reason codes or a rejected→approved status rewrite from creating a new message. Canonical order aliases deduplicate. Fill/position views intentionally have distinct notification IDs but the same source facts. Repeated enqueue returns the existing current entry, including its delivered/canceled state; it cannot requeue it. Changed facts under an already-enqueued source ID raise.

`simulate_delivery(notification_id, action, *, operation_id, as_of, reason_code=None)` permits only:

- PENDING → IN_FLIGHT through START (attempt count increments).
- IN_FLIGHT → DELIVERED_SIMULATED through SUCCEED, or FAILED through FAIL.
- FAILED → PENDING through an explicit RETRY; the next START increments attempts.
- PENDING or FAILED → CANCELLED through explicit CANCEL.

FAIL/CANCEL require a public reason code. Success/start/retry reject unexpected reasons. Terminal states cannot restart; there is no automatic retry, callback, rate limiter or background worker. Delivery operation IDs deduplicate exact callbacks and reject reuse with changed payload. Historical duplicate results never regress current state. All queue and delivery operations require nondecreasing cutoffs, including duplicates. Enqueue and every accepted delivery transition append immutable audit records; malformed/oversized/invalid operations leave the queue unchanged.
