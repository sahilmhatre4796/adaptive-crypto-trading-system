# M9.3 proposal — Offline orchestration and deterministic replay

Status: **frozen M9.3-v1 architecture; implementation requires separate authorization**. Baseline: committed M9.2 `50711faddafc6842be182fff9d6cb73b43997d0b`. M0–M9.2 source, behavior, tests, and the experimental M8 limit of 10% of **current portfolio equity** per trade remain unchanged. No M4, network, Binance/exchange connection, Freqtrade runtime, Telegram transport, credentials, or paper-trading claim enters this scope.

## Scope and actor boundary

M9.3 would accept point-in-time M3/M5/M6 context inputs, complete 5m observations for M7, explicit M8 marks/FX/instrument/cost/funding inputs, and explicit M9.1 simulated full-fill or cancellation commands. The initial run mode is historical `BACKTEST`; it does not download data, infer fills from candles, or import current-only heatmaps into historical decisions. M7 `SignalTracker`, M8 `RiskEngine` plus its `Portfolio`, M9.1 `FreqtradeSimulationBridge`, and M9.2 `OfflineNotificationOutbox` remain the authoritative in-memory actors. M9.3 owns their ordering and a durable journal; it never deserializes an apparent M8 approval as authority.

One **replay unit is exactly one journaled top-level stateful actor invocation** made by the orchestrator, with its complete typed inputs, explicit `as_of`, invocation order, returned result or no-output marker, and public-history deltas. This includes duplicate/cached calls that return an old result while advancing a private chronology cursor. `assemble_context`, `proposal_from_m7`, notification mapping, and snapshots are pure computations whose inputs/configurations are pinned; their outputs are verified against recorded effects where relevant. Calls made *inside* a top-level actor method are **not** additional replay units: `SignalTracker.observe` may invoke `observe_signal`; bridge fills call M8/Portfolio; `bridge.on_signal_terminal` calls M8 terminal handling. Replaying wrapper and nested calls separately would double-apply them. A directly orchestrator-invoked `observe_signal`, Portfolio quote/funding operation, or outbox operation is its own replay unit. No direct, unjournaled stateful actor call is permitted.

The orchestrator records new public `SignalTracker.history/events`, `RiskEngine.history/terminal_history`, `Portfolio.history`, bridge receipts/orders/events, and outbox entries/transitions as **effects of** a replay unit. A transport retry with the *same* command ID returns its journaled receipt without invoking an actor again. A distinct, intentionally issued duplicate actor call has its own command ID and is journaled even if the actor returns a cached result. A cached return is not a new effect and cannot create a second risk job or notification. At replay, fresh actors receive every APPLIED top-level call in sequence, including no-output calls; effects, return identity, and state digest must match. Private dictionaries are never persisted, patched, or treated as authority.

The optional `replay_offline.py` CLI is **deferred** from M9.3-v1. The programmatic interface below covers create, resume, verify and audit needs without a command-line layer; adding a CLI later requires a separate scope decision.

The implementation would expose `create_run(spec, path)`, `submit_frame(frame)`, `advance()`, `drain_notifications(as_of)`, `recover(path, expected_spec)`, and `verify()`. A versioned `RunSpec` pins BACKTEST mode, initial portfolio/currency, M7/M8/M9.1/M9.2 configuration identities, BTC/ETH pair bindings, code/codec versions, and the ordering policy. `ReplayEnvelope` carries `command_id`, kind, source and payload identity, observed and available times, processing `as_of`, explicit source ordinal, causation ID, and payload. `ReplayFrame` is a complete, durably sealed set of commands at one processing cutoff, not a partially dispatchable stream. `StageOutcome` separates orchestration `APPLIED`, `INPUT_REJECTED`, or `HALTED` from business outcomes such as M8 `REJECTED` and `BLOCKED`. No clock default or missing-cost/FX default is allowed.

The semantic run ID derives from initial state and policy, **not** the hash of the entire future input archive. Archive checksums are separate provenance. Appending future data must not change past business IDs. Persist exact source bytes or a lossless canonical encoding and reject unknown schema versions, malformed nested data, or numeric type coercion that would change existing identities. Do not accept a decoded `RiskDecision` as an admission credential: regenerate the actual M8 actor and pass its registered decision and active reservation to M9.1.

## Durable command protocol and writer fencing

Frame submission precedes actor dispatch. In **one SQLite transaction**, persist the complete frame identity, processing cutoff, ordered command IDs and their lossless canonical payload bytes/hashes, declared command count, canonical frame hash, and `SEALED` status. Validate count, order, uniqueness, hash, availability and writer epoch before that commit. No command from an unsealed or partially written frame may be dispatched. A crash while submitting the frame rolls back the whole frame; a crash after sealing leaves the entire frame and its inputs available for recovery. An identical frame retry returns its existing state; a changed frame under the same ID, an inserted command, or a changed order/hash is rejected. Once processing starts, the frame is immutable, including its sealed inputs. A late observation must enter a **new** sealed frame at a strictly later processing cutoff while retaining its original observed/available timestamps; a processed frame cannot be reopened or backdated. A duplicate command ID retains its original journal identity and cannot be moved to a later frame. Derived work remains linked to its committed parent rather than inserted into the root frame.

For each root or derived top-level stateful invocation from a sealed frame or committed parent:

1. In a short SQLite transaction, validate the writer epoch and expected journal head, then durably insert a uniquely keyed `PENDING` command with immutable input hash, cutoff, order, and causation. A repeated ID with identical content returns its existing receipt/state; changed content under that ID is rejected. Derived command IDs come from parent effect, handler version, and ordinal. A root command is never silently renumbered.
2. Invoke the actor **once** against the current graph. Validate its return and capture public-history deltas. Do not acknowledge the command yet.
3. In a second transaction, atomically change `PENDING` to `APPLIED`, append outcome and effects, and create the next durable `PENDING` derived work and notification-job records. Require the same writer epoch and expected head. Commit before acknowledgment. An M8 negative decision is an `APPLIED` command with a negative business result, not an execution failure.

Boundary validation failures before invocation can be recorded as `INPUT_REJECTED`, without touching actors. An actor exception or uncertain second transaction leaves the command non-APPLIED and halts its dependent stream. **Quarantine and discard the entire actor graph** on any actor error, failed commit, ambiguous commit result, epoch mismatch, or expected-head mismatch. Reopen SQLite, resolve whether the command became APPLIED, rebuild fresh actors from the committed prefix, and reconcile the durable PENDING command. Do not continue on or retry against the dirty graph. Automatic retry is allowed only for a proven unapplied, deterministic pending command whose inputs and prerequisites remain valid; an uncertain actor failure requires explicit operator resolution, never a changed payload under the old ID. A crash after APPLIED commit but before acknowledgment returns the committed receipt, without reapplying the command to a live graph.

Use one local writer at a time, SQLite constraints and `BEGIN IMMEDIATE` for writes, a persisted writer epoch plus expected-head compare-and-swap on every phase, and a fresh epoch on recovery takeover. An old writer may have computed a result but cannot commit it after losing its epoch; it must discard its graph. Local disk SQLite with WAL, full synchronous durability, foreign keys, and integrity checks is proposed. Interrupted transactions roll back. Corruption, a missing payload, broken hash chain, identity mismatch, or unreplayable committed prefix halts the run; never repair by deleting a fact or restarting from today's data. SQLite recovery promises replay of **committed local facts**, not exactly-once external delivery or protection from dishonest historical source timestamps.

## Causal schedule and terminal barrier

Only available inputs enter a frame: each source `available_at <= frame.as_of`, with upstream freshness and history checks still enforced by M7/M8/M9.1. An older observation received later keeps its original observation/availability timestamps but receives a later processing cutoff in a new sealed frame; no prior decision is rewritten or backdated. M7's complete eligible 5m history, independent new-candle monitoring, late-observation rejection, and historical heatmap exclusion remain intact. The journal never processes a partially submitted frame, and no later source can be inserted into a frame once it is SEALED.

The versioned same-timestamp **core** order is: (1) available marks/FX and explicit funding on positions already open; (2) explicit exits/cancellations/expiry and monitoring of existing M7 signals, interrupting immediately for any terminal handoff; (3) new M7 context and confirmation observations, again draining any terminal handoff immediately; (4) for each asset in the manifest's priority order, journal one M8 evaluation, then its M9.1 admission/denial, then any required explicit cancellation of a denied active reservation **before evaluating the next asset**; (5) process eligible explicit entry-fill commands only after all asset admission barriers in that frame have resolved. Within a phase and asset, the sealed source ordinal breaks remaining ties. M8 REJECTED/BLOCKED decisions may be passed to the existing bridge `propose` method to record a DENIED receipt, but never yield an order intent or a reservation cancellation. Notification projection/drain is a separate local queue operation after committed core facts; it may lag later frames and is not a competing core phase.

For competing BTC/ETH M8 proposals, `RunSpec.asset_priority` must contain exactly one explicit permutation of `('BTC/USDT', 'ETH/USDT')`; it is frozen in the run manifest and cannot change on recovery. A first-evaluated asset can consume equity, capital, position count, or exposure headroom, reducing or blocking the second. This is deterministic **and priority-biased**, not unbiased. Tests must run both recorded permutations and assert their respective results. Funding-before-exit, terminal-before-new-entry, and all-admissions-before-entry-fills are documented policy, not inferred market truth. A positive M8 reservation already consumes its capital and exposure while its admission is pending; no later asset evaluation is allowed to pass that pending admission.

**Terminal handoff choice:** `bridge.on_signal_terminal(event, as_of=...)` is one journaled top-level replay unit. It internally calls `risk.observe_m7_terminal` and may cancel pending reservations and produce bridge lifecycle notices. Neither the internal M8 call nor its Portfolio cancellations are replayed independently. After **every top-level M7 call**, including `SignalTracker.observe()` on a consumed candidate and direct `observe_signal()`, compare the complete `SignalTracker.events` history with its pre-call history. Commit any newly generated terminal effects with deterministic, durable terminal-handoff `PENDING` children in their original event order. Immediately drain those handoffs before the next stateful core call, later M7 call, risk evaluation, admission, fill, or frame. This applies during both monitoring and new-context processing; a terminal generated in the new-context phase cannot wait until a later scheduled phase. Until every child is APPLIED, the barrier remains closed. If risk inputs fail later, the committed M7 terminal and completed or pending handoff remain first in recovery order. A failure inside handoff halts the dependent core stream and requires recovery; it does not erase the M7 fact. If no bridge order exists, the same bridge call still delivers the terminal to M8 and is journaled even if no bridge notice appears. Terminal notices for open positions do not execute exits.

## M8 approval and stalled reservations

The orchestrator calls M8 `evaluate` before bridge `propose`. Only the actual decision in connected M8 history with `APPROVED`/`REDUCED` status and its active matching Portfolio reservation can cross M9.1's gate. M8 `REJECTED`/`BLOCKED`, fabricated/modified/stale decisions, old reservations, and raw decoded objects cannot create an intent. Entry fills still use the bridge's M8 `simulate_open` recheck; no M9.3 code sizes or authorizes trades.

A positive M8 decision and reservation may commit before M9.1 admission. Its durable derived admission command is then **PENDING**, and a barrier prevents new risk evaluations, admissions, or fills until that admission resolves. On crash, recovery reconstructs the reservation and applies the pending admission at the original recorded cutoff; it never invents a new grant or silently drops the reserve. If admission is ACCEPTED, the reservation remains active until an explicit eligible fill, cancellation, expiry, or terminal. If admission is DENIED while the reservation is still active, commit the denial, then enqueue an explicit, deterministic Portfolio cancellation command and keep the barrier until that cancellation is APPLIED; record its reason and event ID. If the reservation is already absent because a committed terminal handoff canceled it, record that fact and do not cancel it again. If denial/cancellation cannot be reconciled, halt with the reservation visible in the rebuilt portfolio. An interrupted admission remains PENDING, with the reservation visible; it is not automatically released. This rule does not alter the existing M8 formation-consumption decision or allow requalification.

## Notification isolation

Core APPLIED effects and notification jobs commit together. For v1, notification processing is a **logical FIFO queue under the same fenced SQLite journal owner**, not a separate process, connection with independent writer authority, or second actor graph. The owner calls pure `notification_events` and then the outbox's top-level `enqueue` or `simulate_delivery` operations as separate journaled steps. It never calls risk or order mutators from a notification job. Jobs receive a persistent monotone sequence when their source effect commits; process by that sequence and stable within-source view ordinal, not original market timestamp or asset name. Canonical aliases and multi-view fill notifications use stable job IDs; each enqueue is a separate durable unit because M9.2 offers no atomic batch. An explicit `drain_notifications(as_of)` cutoff must be no earlier than the source fact's availability, the last committed journal processing cutoff, and the outbox's last operation cutoff. Before draining at that cutoff, finish every sealed core frame at or before it; do not advance the notification clock past an unfinished earlier core frame. Reject or defer an earlier cutoff; never silently replace it with a generated timestamp or backdate an older source. Delivery actions have their own explicit nondecreasing cutoffs and persistent operation order. A delayed older-source job following a newer core frame appends later in FIFO arrival order while retaining its original source timestamps. A rendering/enqueue/delivery failure records a local M9.3 job failure and leaves committed M8/M9.1 facts unchanged. No recursive failure notification is attempted for a renderer failure. M9.2 `ProcessingFailure.stage` has no M9.3 value; journal/codec failures remain M9.3-local audit facts, not mislabeled M9.2 records.

An `IN_FLIGHT` outbox entry reconstructs as `IN_FLIGHT`. Restart does not invent a `SUCCEED`, `FAIL`, or `RETRY`; only a later explicit, journaled operation changes it. A `DELIVERED_SIMULATED` state is a local simulation fact, never a Telegram acknowledgment. Notification backlogs may lag core processing without changing risk, reservations, or order state. If the shared journal itself cannot durably record core work, core processing halts; this is a storage failure, not a notification failure.

## Acceptance tests and verification gate

All tests use deterministic fixtures, fresh actors, isolated temporary SQLite databases, and no paid API or network. Implementation must run targeted M9.3 tests, the complete existing suite, configured checks, staged-scope/preservation verification, and a full diff review before any later commit request. Required tests include:

1. Crash after actor mutation but before APPLIED/effects commit: PENDING remains, dirty actors are discarded, fresh replay applies it once, and no phantom grant/order survives.
2. Crash after APPLIED/effects commit but before acknowledgment: retry returns the original receipt and creates no second reservation, fill, or notification job.
3. M7 terminal committed before later malformed risk inputs; terminal and pending/finished handoff survive, and no later risk/admission/fill overtakes the barrier.
4. Notification render/enqueue failure after successful M9.1 admission; M8 portfolio/reservation and bridge histories equal a control run. Failure between the two notifications from one fill leaves the first committed and the second pending.
5. Recover an `IN_FLIGHT` outbox item without inventing delivery or retry; exact recorded delivery commands reproduce private outbox chronology.
6. Duplicate/cached `SignalTracker.observe`, direct `observe_signal`, `RiskEngine.evaluate`, bridge callback, and outbox calls with no new public effect; replay reproduces their chronology and later earlier-time rejection. Nested actor calls are **not** double-replayed.
7. A stale second writer fails epoch or expected-head validation after computing on its own graph and discards that graph; no competing effect commits.
8. SQLite interrupted transaction rolls back; rollback/commit error, corruption, missing payload, broken chain, and incomplete PENDING state yield explicit recovery or fail-closed outcomes.
9. Code, codec, schema, or configuration identity mismatch fails recovery before actor mutation.
10. Approved M8 decision with unfinished M9.1 admission reconstructs with its reservation; accept/deny/cancel continuation is deterministic. Fabricated, modified, expired, stale, or unregistered decision/reservation cannot pass bridge admission.
11. Both manifest-recorded BTC/ETH priorities under simultaneous capital contention; repeat runs preserve their chosen outcomes and reveal the priority effect. Funding/exit and terminal/entry same-cutoff cases follow the frozen phase order.
12. Prefix invariance and future-data mutation; committed past business IDs and outcomes remain unchanged. Compare uninterrupted and interrupted/recovered runs across every stage, including exact IDs, risk decisions, reservations, balances, reasons, source timestamps, order states, outbox states, audit effects, and notification bodies.
13. Crash before the atomic frame-seal commit leaves no dispatchable commands; crash after sealing leaves the complete counted/ordered/hashed frame. Reject a changed frame, command insertion, and attempts to alter a processed frame; a genuinely late input uses a strictly later processing cutoff.
14. Two same-cutoff asset candidates run under BTC-first and ETH-first manifests. Each M8 decision is followed by its bridge admission and, on denial with an active reserve, a committed cancellation before the next asset evaluation; eligible entry fills follow all resolved admissions. Assert the resulting capital-allocation bias and replay equality.
15. A consumed `SignalTracker.observe()` emits a terminal during new-context processing; its committed handoff preempts the next core call. Inject a crash between terminal APPLIED and handoff APPLIED, then recover and prove no risk evaluation, admission, fill or later frame overtook it.
16. Process a delayed older-source notification after a newer core frame under the same fenced owner. Assert persistent FIFO job/view order, nondecreasing explicit enqueue and delivery cutoffs, unchanged original source timestamps, and exact outbox state/timestamp equality after recovery.

No test result is claimed by this proposal. Earlier milestone tests are historical until rerun for an authorized implementation.

## Decision log

**Frozen design decisions:** replay units are top-level stateful actor invocations including no-output calls; nested calls are never separately replayed. Complete frame identity/count/order/hash and SEALED status commit atomically before dispatch, and processed frames cannot be changed. The journal uses durable PENDING then atomic APPLIED/effects/jobs, with graph discard on failed/uncertain commit. `bridge.on_signal_terminal` is one top-level unit; every M7 call is checked for newly generated terminal events and its handoff barrier is drained immediately. The same-cutoff core sequence is versioned: marks/funding; exits/monitoring; new context; **per-asset M8 evaluation → M9.1 admission → denied-reservation resolution**; then eligible entry fills. Asset priority is mandatory and immutable per run, with no hidden default or fairness claim. Positive M8 reservations persist through unfinished admission; a denied admission with an active reserve requires explicit journaled cancellation. M8 negative decisions may yield DENIED bridge receipts but never order intents. Notifications are independent local projections processed in FIFO order by the same fenced journal owner with explicit nondecreasing cutoffs. Recovery replays committed local facts only; there is no external exactly-once guarantee.

**Approved design choices:** offline orchestration and deterministic replay only; a transactional standard-library SQLite journal with one fenced writer; explicit BTC/ETH priority recorded in each run manifest; preservation of all M7–M9.2 interfaces; and no live Binance, Freqtrade or Telegram integration. M9.3-v1 retains the BACKTEST-only, point-in-time context-input scope above. Both asset-priority permutations are supported, but each concrete run must supply exactly one; there is no default. The optional CLI is deferred. No service, package purchase, or live capability is implied.

**Authorization still required:** explicit permission to begin M9.3 implementation. This frozen architecture and its commit authorize design preservation only, not code or test creation. A concrete run's explicit asset priority is input data, not an unresolved architecture choice.

**Deferred to implementation:** exact SQLite tables/constraints, atomic frame-seal transaction layout and busy-timeout settings; exact codec field layout and error enums; process-fault injection mechanism; public receipt formatting; audit export format; benchmark measurements; and whether later read-only checkpoints improve recovery time. These may not weaken the invariants above. The optional CLI and any external transport are outside M9.3-v1. M9.2's now-committed baseline removes the earlier untracked-file gate. Any upstream interface change found during implementation would require a proposal revision rather than a silent M0–M9.2 modification.
