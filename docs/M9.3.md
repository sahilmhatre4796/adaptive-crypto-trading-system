# M9.3 — offline orchestration and deterministic replay

M9.3 connects the existing M7 signal tracker, M8 portfolio risk engine, M9.1 simulation bridge, and M9.2 local notification outbox. It is **offline BACKTEST mode only**. It does not fetch market data, infer fills, place orders, call Freqtrade, or deliver Telegram messages. The user-selected M8 planned-loss limit remains 10% of **current portfolio equity**, enforced by M8 rather than duplicated here.

## Modules and API

- `trading/replay_codec.py` encodes allowlisted, typed model values as canonical JSON. Decimal representation, integer versus float identity, UTC nanosecond timestamps, schema version, and field names survive a round trip. Pickle and payload-directed imports are excluded.
- `trading/replay_journal.py` stores the run manifest, sealed frames, top-level actor commands, effects, derived work, and notification jobs in a local SQLite database. It uses WAL, `synchronous=FULL`, foreign keys, `BEGIN IMMEDIATE`, a single writer epoch, expected-head checks, and a hash chain.
- `trading/orchestration.py` owns the fresh actor graph and the ordered calls. `RunSpec` pins initial cash/currency, upstream configs, explicit BTC/ETH bindings and priority, template config, and BACKTEST mode. `create_run(spec, path)` makes a new database; `recover(path, expected_spec)` verifies identity and replays committed calls into fresh actors. `submit_frame(frame)` seals a full frame; `advance()` applies one pending core call; `receipt(command_id)` returns a committed result without invoking an actor; `drain_notifications(as_of=...)` projects jobs; `simulate_delivery(...)` records local outbox transitions; `verify()` checks local storage and returns state and chain digests.

`ReplayEnvelope` carries a caller-supplied command ID, source ID, observed time, availability time, processing cutoff, source ordinal, typed payload, and optional causation ID. `payload_id` is its canonical SHA-256. `ReplayFrame` has a caller-supplied ID, a single cutoff, unique commands and ordinals, count, and canonical hash. Every root command in a frame is inserted in one transaction with the frame's `SEALED` marker; none is dispatchable before that commit. A changed frame or same-cutoff late frame is rejected. Late inputs require a cutoff strictly later than prior frames and committed outbox work. Unknown or malformed source payloads never become assumed prices, fees, FX, or approvals.

## Causal order and actor boundary

At one cutoff the frozen order is: (1) marks/FX, then explicit funding; (2) explicit exits, cancellations, expiry, and monitoring; (3) new M7 context; (4) for each asset in `RunSpec.asset_priority`, M8 evaluation followed immediately by M9.1 admission and any required explicit denial release; (5) eligible entry fills. Source ordinal breaks ties. A BTC-first run and an ETH-first run can allocate scarce capital differently. This is deterministic **priority bias**, not fairness. The priority is part of the manifest and cannot change on recovery.

Exactly one journal record represents each top-level stateful actor invocation, including cached and no-output calls. Internal M7 monitoring during `SignalTracker.observe`, internal M8/Portfolio calls in bridge methods, and internal Portfolio calls in M8 are not replayed separately. New M7 terminal events create durable `bridge.on_signal_terminal` children. The terminal child must finish before the next core call, even when the terminal arose from a consumed context observation. Its bridge call performs the M8 terminal handoff internally. An M8 decision creates an admission child; a positive reservation remains visible while that admission is pending. A denied positive admission with an active reserve creates a separate durable Portfolio cancellation child. Negative M8 decisions can yield DENIED receipts, never order intents.

The bridge receives only the actual M8 actor's registered `RiskDecision`; root ADMIT and order commands are prohibited. A `RISK` root contains the authentic M7 signal ID, typed instrument specification and cost model, leverage, and optional requested quantity. The orchestrator builds its proposal from the registered M7 record. M3/M5/M6 context arrives as typed, point-in-time input to `assemble_context`; the existing M7 and M6 historical eligibility checks remain authoritative. Present-day heatmap snapshots cannot be inserted into a historical run through this boundary.

## Durability and recovery

A complete input frame first commits root commands as `PENDING`. An actor is then invoked, and a second transaction atomically records `APPLIED`, result or no-output marker, public-history effects, state digest, derived commands, and notification jobs. If mutation occurs before effects commit, the graph is quarantined; recovery replays the committed prefix in new actors and resumes the pending command. If effects commit succeeds but acknowledgment is lost, the journaled `receipt` is returned on retry. Any failed or uncertain effects commit invalidates the entire in-memory actor graph. Recovery never patches private actor dictionaries.

Recovery validates SQLite integrity, foreign keys, manifest and code identity, canonical payloads, sealed frame roots and dispatch order, frame completion, applied-command chain, derived terminal/admission work, job FIFO, recorded results, public effects, and actor state digests. Corruption, missing facts, a changed configuration, or divergent actor replay halt rather than silently repair the run. An old writer is fenced by the new epoch; a writer whose expected head changed cannot commit. This is a single local writer design, not a distributed consensus or external exactly-once protocol.

## Notification projection

Core effects and notification-job records commit together. The same journal owner processes jobs in persistent FIFO order. One rendered view is one top-level outbox enqueue command. Enqueue and simulated-delivery cutoffs are explicit and nondecreasing; the original source timestamps remain attached to notices even when jobs are drained after newer frames. The drain refuses an unfinished earlier core frame. Mapping or rendering failure marks only that local job failed; M8 decisions, reservations, balances, and M9.1 order states are not revised. A commit uncertainty instead quarantines the actor graph. On recovery, `IN_FLIGHT` stays `IN_FLIGHT` until an explicit journaled follow-up operation. `DELIVERED_SIMULATED` is a local test state, never a Telegram acknowledgment.

## Test coverage and limits

The focused suite uses synthetic M3/M5/M6 fixtures, no provider or network. It covers canonical round trips, atomic frame sealing, rollback, corruption, writer fencing, both BTC/ETH priorities, M7 terminal barriers, cached calls, M8 approval enforcement, pending reservations, explicit funding/exit order, notification FIFO, multi-view interruption, and reconstructed IDs/state. A test-only bridge double forces an otherwise defensive approved-then-DENIED path so interruption before explicit release is exercised; normal same-cutoff admission with valid inputs does not naturally enter that branch. See `docs/coordination/M9.3-TESTS.txt` for the final fresh command results.

The input source's historical timestamps and truthfulness cannot be proven by SQLite. This milestone does not validate market profitability, execution realism, external delivery, or paper-trading readiness. Recovery replays committed **local** facts; it does not guarantee exactly-once effects in any external system. Full-prefix replay costs time proportional to the number of applied commands, and a local SQLite file still needs ordinary filesystem backups and integrity monitoring.
